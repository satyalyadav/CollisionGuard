# CollisionGuard evaluation and experiment plan

Research date: 2026-11-07. The [proposal](../proposal/original-proposal.md) targets pre-execution prediction. Recommendations are design choices, not measured results; an online scheduler needs further evidence.

## Decision time and eligible pairs

Define the operational decision as dispatching two ready tasks together from a known repository snapshot, before either task's execution. Both task descriptions, assignments, base snapshot, and all features must exist at that instant. For a retrospective pair, record the latest time at which both were known ready and still unstarted; exclude pairs where no such time is demonstrable. Issue creation, PR creation, first commit, and co-activity are imperfect readiness and start proxies. Report proxy error and pairs with unknown ordering. A prediction after the first start belongs in a separate analysis.

Version every input as of the decision time. GitHub's [issue schema](https://docs.github.com/en/graphql/reference/issues) exposes edit-related fields, but their presence alone does not prove that an old title and body can be reconstructed. Require a timestamped archived snapshot or a verifiable reconstruction of each field. Accept a current field only when evidence establishes it was unchanged after the cutoff. Treat missing edit history as unknown, not proof of no edits; exclude the affected field or pair from the primary analysis and report coverage. Apply the same check to comments, links, labels, agent identity, and repository metadata. Exclude later PR text, diffs, final files, and completion times. Fix the encoder version and disclose possible pretrained-model exposure to later material; frozen embeddings do not by themselves establish historical availability.

The proposed co-active-PR filter selects pairs using outcomes observed after dispatch. It estimates performance conditional on historical co-activity, not on every pair an online scheduler could consider. Construct a second, separately reported candidate population from task readiness and known availability at decision time, including pairs that did not historically overlap where both resulting changes can be replayed. Define eligibility, sampling probabilities, and denominators before inspecting labels; weight unequal probability samples and describe excluded tasks. If readiness or a representative candidate frame cannot be reconstructed, label all metrics as conditional retrospective estimates and do not claim deployment prevalence or scheduler benefit.

## What replay measures

Pin Git version, configuration, base and head IDs, task-to-PR mapping, and pair ordering. Replay fixed historical heads with their actual common merge base. Git's [`merge-tree` documentation](https://git-scm.com/docs/git-merge-tree/2.45.0) specifies clean, conflicted, and error outcomes; without `--stdin`, exit codes 0, 1, and other values distinguish them. In batch mode parse each result rather than the process exit code. Report missing objects and operational errors as unavailable, not clean. Git conflicts include rename, binary, and file/directory cases, so either call the outcome a Git-reported merge conflict or explicitly define and validate a narrower textual subset.

A head-to-head replay is a target for those historical histories, not proof of what two agents would write from the common snapshot. Heads may contain inherited changes or resolutions, and their bases may differ. Audit ancestry and shared bases, inspect a stratified sample, and report a cleaner common-base subset separately. A common-base patch reconstruction is a sensitivity test, but failures are inconclusive and reconstructed patches are not counterfactual agent work. A clean Git merge does not establish passing tests or semantic compatibility.

This distinction matters for the file model. A [2026 lineage preprint](https://arxiv.org/html/2610.04779) reports 79 of 167 conflicts with disjoint authored file sets in a stratified 715-pair sample, explaining the mismatch between per-PR bases and the heads' common merge base. This selected sample is not a population rate or a comparable pre-execution result. Use actual overlap only for error analysis.

## Splits, features, and baselines

Reserve repositories for a final untouched test set before tuning. Within development repositories, use grouped validation with no repository in both training and validation; scikit-learn's [GroupKFold](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html) enforces group separation, not time ordering. For the stronger future-unseen-repository test, choose a global cutoff: all training features and labels must have become available before it, while held-out repository decisions occur after it. Keep repositories disjoint across those sets. Separately test forward in time within known repositories. Purge pairs that cross boundaries, and assert that no issue, task, PR, duplicate, or linked task family crosses any split. Assign tasks before forming pairs or partition connected components of the task-pair graph; discard cross-partition edges rather than leaking a task through another pair. Report the number dropped and label availability lag. If a strict intersection leaves too few positives or repositories, report that limitation instead of weakening the split silently.

Start with a prevalence-only predictor, then issue title/body TF-IDF cosine similarity, and class-weighted logistic regression using pairwise text similarity plus simple features known at dispatch. Add one fixed embedding cosine baseline only if locally available. A direct boosted classifier can use the same permitted inputs. Fit vocabulary, scaling, feature selection, tuning, calibration, and thresholds inside training folds only. Match candidate pairs, splits, features, and compute budget across models. Use file-path keyword or TF-IDF retrieval as a footprint baseline. Include agent identity only if assigned at dispatch, and report a no-identity model.

For unseen repositories, a global classifier over training path IDs cannot predict new paths. Instead, at each cutoff rank the files actually present in that repository snapshot using task-to-path and optionally task-to-file-content retrieval. Train any learned scorer across repositories using transferable textual or structural features, not repository-specific labels. Measure task-level recall@k and precision@k against the eventual changed files, plus coverage for added, renamed, deleted, or otherwise absent paths. A snapshot-only candidate list cannot retrieve new paths. Exclude future file contents and history.

For stacking, generate each training task's footprint scores out of fold using a model that saw neither that task nor its repository in the applicable fold and only earlier labels where the temporal protocol requires it. Build pair-overlap features from those out-of-fold scores, then train the conflict model. Fit a fresh footprint model on the permitted outer-training data to produce outer-validation or test scores; all tuning and calibration remain nested. Use the same repository and task isolation at both stages, and never fit the first stage on a pair's eventual files before generating that pair's training features. Compare direct versus direct plus predicted overlap with identical conflict-model inputs and tuning. Ablate footprint features, text features, and history individually. Include actual-file overlap only as a labeled diagnostic.

The [2019 merge-prediction study](https://arxiv.org/abs/1907.06274) reports conflict-class F1 of 0.57 to 0.68 across languages using Git-derived features on historical merge scenarios. Its timing, features, splits, and prevalence differ, so this is context, not a pre-execution target. A direct replication is meaningful only if all inputs meet CollisionGuard's cutoff.

## Metrics and scheduling

Use average precision (AP) as the named primary ranking metric; report prevalence and the full precision-recall curve. Scikit-learn's [AP definition](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html) is non-interpolated and differs from trapezoidal PR-AUC, so report both by their exact names if both are used. Show precision at fixed recall and recall at a fixed review or delay budget, with thresholds selected on validation data. Report confusion counts, precision, recall, and F1 at the frozen threshold. Report pair-weighted and per-repository results, positive counts, and repository-cluster bootstrap intervals for paired differences. Disclose unstable intervals.

Evaluate probability quality with reliability plots, Brier score, and log loss on the natural candidate distribution. Fit calibration only on separate grouped, time-valid development predictions; compare uncalibrated and calibrated results, since class weighting or case-control sampling can change probability interpretation. The [scikit-learn calibration guide](https://scikit-learn.org/stable/modules/calibration.html) explains reliability curves and calibration methods. A score calibrated on co-active pairs need not be calibrated for all ready pairs.

Simulate event-by-event dispatch on held-out repository streams using the same arrivals, agent capacity, deterministic tie-breaking, task durations, and integration rules for every policy. Compare unrestricted parallelism, FIFO serialization, a similarity threshold, the learned risk threshold, and a labeled oracle using frozen replay labels. Select thresholds and any delay budget on development streams. Report conflict-labeled pairs actually run concurrently, missed-conflict fraction with its denominator, parallelism, mean and tail wait, makespan, and inference latency. Vary duration and capacity assumptions and report label coverage; unknown edges are not clean. Historical durations are simulation inputs, not prediction features.

Frozen replay labels and durations assume task outputs and timing remain unchanged under a different schedule. Serial execution could change the base, patch, duration, and conflict outcome, so reductions are avoided *frozen-label concurrent risk*, not measured causal reductions in real merge conflicts. Incomplete workload coverage precludes a delay/conflict optimum. CooperBench can be a separate stress test if compatible labels and uncontaminated inputs are available: its [dataset documentation](https://github.com/cooperbench/CooperBench/blob/main/dataset/README.md) reports 499 of 652 gold patch pairs conflict, reflecting constructed overlapping work rather than ordinary online prevalence.

## Ordered gates

1. **Pilot and validity.** On a stratified sample, audit decision times, versioned text, candidate eligibility, ancestry, and replay results by hand. Proceed only if the team can state the cutoff, reproduce labels, distinguish unavailable outcomes, and quantify exclusions. Otherwise narrow the claim and fix the data contract first.
2. **Baseline and footprint.** Freeze splits and the metric protocol. Run prevalence, text similarity, and logistic baselines. Proceed to stacking only if the held-out-repository file retriever beats a declared cheap path baseline on recall@k with adequate snapshot coverage. Report a null result if it does not.
3. **Model and ablation.** Produce out-of-fold footprint features, then compare direct and two-stage models on identical development folds. Freeze choices before one test evaluation. Claim incremental value only if the paired repository-cluster interval and practical operating-point gains support it; otherwise report uncertainty or no demonstrated benefit.
4. **Simulation.** Proceed only with reconstructable task streams, decision-time inputs, adequate replay-label coverage, and frozen policies. Report the full wait versus frozen-risk tradeoff and its assumptions. If these conditions fail, stop at retrospective prediction and identify a prospective or controlled agent experiment as the next step.
