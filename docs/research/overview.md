# CollisionGuard research findings and next steps

Research date: 7 November 2026. This assessment is separate from the [fixed proposal snapshot](../proposal/original-proposal.md). Three focused investigations cover [prior work](prior-work-and-novelty.md), [data feasibility](data-and-label-feasibility.md), and [experimental design](evaluation-and-experiments.md). Published results below are author-reported, checked against primary sources, and have not been independently reproduced here.

## What the project does

Given two coding tasks and a repository snapshot, CollisionGuard estimates whether the tasks' eventual changes will produce a textual Git merge conflict. Its distinguishing constraint is timing: every predictive input must exist before either agent starts coding. The proposed comparison asks whether predicting each task's likely files adds useful information beyond directly classifying the task descriptions and allowed repository metadata.

A scheduler could delay risky pairs while allowing other work to run. The prediction study and scheduling study need separate evidence. A classifier can rank historical conflicts without proving that rescheduling agents reduces real conflicts. A clean textual merge also says nothing about semantic compatibility or passing tests. [Git merge-tree documentation](https://git-scm.com/docs/git-merge-tree)

## How novel is it?

The broad ideas have substantial prior work. TAITIr predicts task file interfaces from acceptance tests and uses their intersection as conflict risk. Cassandra schedules tasks using expected edit locations and dependencies. Crystal checks speculative merges of changes already written. These precedents rule out a broad claim that anticipating task collisions or scheduling around them is new. [TAITIr paper](https://pauloborba.cin.ufpe.br/publication/2023using_acceptance_tests_to_predict_merge_conflict_risk/2023-Rocha-Using%20acceptance%20tests%20to%20predict%20merge%20conflict%20risk_1%20copy.pdf), [Cassandra paper](https://web.engr.oregonstate.edu/~sarmaa/wp-content/uploads/2020/08/2486788.2486884.pdf), [Crystal paper](https://people.cs.umass.edu/~brun/pubs/pubs/Brun11fse.pdf)

MergeGym is the closest recent agent-specific work in the proposal. Its scope predictor uses information available at PR opening, while its textual-conflict model uses existing changes and branch lineage. PR opening does not establish availability before coding. Its targets and input timing therefore differ from the proposed primary experiment. [MergeGym paper](https://arxiv.org/html/2610.04779)

Our judgment is that a narrower contribution is plausible:

> Evaluate pairwise textual Git conflict prediction using only information demonstrably available before both agent tasks start, and test whether predicted file overlap improves prediction on unseen repositories.

This is a defensible research question, not a verified first-of-its-kind claim. A useful result could be a well-controlled negative finding that file prediction adds little, or that strict pre-start evidence is too sparse for the proposed data source. The study should not depend on inventing a new classifier architecture.

## What existing work can we use?

Use the 2019 conflict-prediction paper for classical Git-feature baselines and its replication artifact for implementation guidance. Its reported conflict-class F1 ranges across languages, but its observed branch features and evaluation protocol differ from CollisionGuard. Its scores are background context, not a performance target. [Paper and author artifact](https://github.com/ualberta-smr/conflict-prediction)

Use the agent PR study's replay protocol and replication artifacts to learn the label construction. Its sample has 747 pairs, of which 716 were evaluable and 167 conflicted. These selected pairs are a useful reproducibility check, not an estimate of the prevalence among all ready tasks. Check for overlap before using the sample as independent validation. The Zenodo record API was accessible, although the DOI page failed and the archive binary was not downloaded or compared with the GitHub mirror. [Study](https://arxiv.org/html/2607.04697), [author artifact](https://github.com/Quantum535/concurrent-agentic-prs-replication), [Zenodo record API](https://zenodo.org/api/records/21186464)

Use MergeGym to motivate a lineage audit. Authored-file sets measured against separate PR bases can be disjoint even when merging the resulting heads conflicts. Predicting file overlap is therefore a proxy that needs an ablation, not a safety guarantee. Its models have access to changes that a pre-start predictor cannot use. [MergeGym](https://arxiv.org/html/2610.04779)

Use AIDev as a candidate source of issue-linked tasks, commits, and eventual changed-file training labels. The dataset card describes the proposal's linked v5 snapshot as frozen and byte-identical to the main dataset's v5 tag, with a March 31, 2026 cutoff. We have not independently compared their file hashes. Pin an immutable revision and verify file hashes before constructing the benchmark. Select columns and repositories without loading the full tables into RAM. [AIDev snapshot card](https://huggingface.co/datasets/hao-li/AIDev-7.6M)

The proposed v4 fallback needs a design change. Its inspected file tree lacks the issue and issue-link tables used by this pipeline. It cannot replace v5 without another audited source of historical task descriptions and associations. The inspected v5 schemas also lack issue edit history and explicit coding-start evidence. Dataset size is therefore less important than the yield of examples with defensible provenance. [v4 file tree](https://huggingface.co/datasets/hao-li/AIDev/tree/v4), [data feasibility report](data-and-label-feasibility.md)

Use CooperBench as a possible controlled stress test. It has feature descriptions, base environments, and patches, but its gold feature patches were split from combined changes and are not intended to merge directly. Gold-patch conflicts would define a distinct target from conflicts between agent-produced patches. Version the task data and explain which target is measured before calling it external validation. [Official dataset documentation](https://github.com/cooperbench/CooperBench/blob/main/dataset/README.md)

## Gaps that matter most

1. **Prove the input cutoff.** Historical PR creation is not execution start. A current issue body may contain later edits. A retrospective pair may never have had an instant when both tasks were ready and neither had started. Record evidence for readiness, start, and text version, and report the usable yield. Otherwise the primary novelty claim cannot be tested with that cohort.
2. **Define the target and population.** Historical co-active PRs are a selected population. Their final heads may include inherited changes from different bases. Audit lineage, record the exact replay contract, and distinguish unavailable objects from clean merges. Report results as retrospective and conditional when the data cannot support a dispatch-time candidate population. [Git documentation](https://git-scm.com/docs/git-merge-tree)
3. **Prevent leakage through both stages.** Keep repositories and repeated tasks out of opposing folds. Produce training footprint predictions out of fold. A footprint model that already saw a task's eventual files would give the conflict model misleadingly good training inputs. For unseen repositories, rank files in the actual pre-start snapshot rather than classifying over a fixed vocabulary of training-repository paths. [Grouped validation](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.GroupKFold.html)
4. **Measure practical value.** Define whether the primary metric is average precision or trapezoidal PR-AUC. Report prevalence, operating points, calibration, and uncertainty across repositories. A frozen-label scheduling simulation measures a tradeoff under fixed outputs and durations; it does not establish a causal reduction in future agent conflicts. [Average precision](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html), [calibration guide](https://scikit-learn.org/stable/modules/calibration.html)

## Recommended next steps

These are recommendations, not completed experiments or changes to the fixed proposal.

1. **Write the data contract and audit a small pilot first.** Sourish starts with 20 candidate pairs across at least five repositories, selected before inspecting their labels or ease of recovery. Suggested planning gates are at least 10 fully valid pairs spread across at least five repositories, within six person-hours of recovery work and 2 GiB of downloads. A valid pair needs verified pre-start task text and associations, a defensible common decision time, immutable replay inputs, and a reproducible label. Record these thresholds before sampling; do not loosen them afterward to make the pilot pass. Expand toward 100 only if the gates pass. These are feasibility gates, not statistical guarantees or enough to promise a final score. For every attempted pair retain the task text and its provenance, the common prediction time, start-time evidence, repository snapshot, task-to-PR links, exact heads and merge base, replay outcome, and exclusion reasons. Publish the selection funnel and recovery costs. If strict historical evidence fails or the budget runs out, investigate the failure, choose a controlled task set, or explicitly narrow the setting before expansion.
2. **Freeze splits and build cheap baselines.** Satyal leads prevalence, TF-IDF similarity, logistic regression, and one direct boosted classifier on identical permitted inputs. Kishore freezes repository-disjoint validation and a separate forward-time check, plus the exact AP or PR-AUC definition. Use validation data for thresholds and calibration. Quantify uncertainty before claiming an improvement.
3. **Test file prediction incrementally.** Yin starts with task-to-path retrieval on each pre-start repository tree. Measure footprint recall and absent-path coverage on held-out repositories. Add learned retrieval only if needed. Compare the direct classifier with and without out-of-fold predicted overlap under the same tuning budget. Report a null result if the extra stage does not help.
4. **Simulate scheduling after the predictor is credible.** Kishore compares unrestricted parallelism, FIFO serialization, a simple similarity rule, and learned risk gating on the same task streams and capacity assumptions. Report waiting time and makespan as well as frozen conflict exposure. If stream or label coverage is inadequate, finish the prediction study and reserve prospective scheduling for later work.

The immediate deliverable should be a data-quality report and reproducible baseline dataset. Large downloads, optional pretrained decision models, and a full agent scheduler can wait until the pilot establishes that the central claim is measurable.

## Scope and verification

The original proposal is preserved as Markdown in `docs/proposal/`. The conversion checks found matching source text token counts and retained all nine distinct embedded link targets. At the user's request, the redundant PDF copy and conversion audit files were later removed. The project history is in [PROGRESS.md](../../PROGRESS.md). No Git commit or remote backup was created during this work.

The initial research used papers, official documentation, dataset cards, and author artifacts. At that stage no source data was downloaded in bulk, no merge replay was executed, and no model was trained. The subsequent [exploratory pilot](../pilot/results.md) downloaded pinned source tables and attempted current-head diagnostics. It remains inconclusive because the primary historical evidence was not queried. No model has been trained. The pilot report records its Opus review, corrections, and reproducibility limits.
