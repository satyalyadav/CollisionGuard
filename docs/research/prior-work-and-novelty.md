# Prior work and novelty for CollisionGuard

Research note, 7 November 2026. This bounded investigation checked the proposal's references [1], [4], [5], and [6] against their papers, and searched for work on anticipating conflicts before implementation. The numerical results below are results reported by the authors, checked against the cited primary texts, not independently reproduced. A text conflict means a conflict reported by a Git merge operation; file overlap is a risk proxy, and a clean textual merge does not establish behavioral correctness.

## Closest work before coding

**Acceptance-test interfaces.** Rocha and Borba's TAITIr is the most direct threat to a broad claim that predicting future task collisions by estimating file footprints is new. Its intended setting is behavior-driven development, where acceptance tests are written before application code. It derives a predicted task file interface from each task's Cucumber tests and flags intersecting interfaces as conflict risk. The authors retrospectively extracted 990 tasks from 19 Rails projects and assessed 6,360 possible task pairs, including some actually concurrent pairs. At a threshold of one common predicted file, they report precision 0.59 and recall 0.98, flagging 96.70% of pairs. The label is *actual shared changed files*, not a Git textual merge conflict. Their retrospective analysis used final versions of tests, which may have evolved during implementation, so it does not demonstrate a strictly pre-coding evaluation. The approach also requires task-specific acceptance tests and Rails/Cucumber support. [Rocha and Borba, 2023](https://pauloborba.cin.ufpe.br/publication/2023using_acceptance_tests_to_predict_merge_conflict_risk/2023-Rocha-Using%20acceptance%20tests%20to%20predict%20merge%20conflict%20risk_1%20copy.pdf); [authors' study site](https://thaisabr.github.io/conflict-risk-prediction-study-site/).

**Task scheduling.** Cassandra already schedules tasks to reduce expected conflicts using developer-provided files to edit, inferred file dependencies, task dependencies, and developer preferences. Its evaluation used historical scenarios from four open-source projects and simulated scenarios. The authors report that it could avoid a majority of conflicts in their four test subjects, under their model and retrospective inputs. This is evidence against claiming conflict-aware task scheduling itself as novel, but it does not establish task-text prediction of Git conflict labels before both tasks begin. [Kasi and Sarma, 2013](https://web.engr.oregonstate.edu/~sarmaa/wp-content/uploads/2020/08/2486788.2486884.pdf).

Brun and colleagues also described predicting future development trajectories and conflicts *before conflicting edits* as a research vision in 2012. They proposed predictions based on histories and speculative future actions, rather than presenting a validated task-text model. The idea of anticipating a conflict before it exists therefore predates both projects. [Brun et al., 2012](https://people.cs.umass.edu/~brun/pubs/pubs/Brun12fcsd.pdf).

## Proposal references and decision points

**[1] Crystal, 2011.** The citation and DOI identify Brun, Holmes, Ernst and Notkin's *Proactive Detection of Collaboration Conflicts*. Crystal speculatively merges existing developer changes, then builds and tests the merged result. Its input is therefore code already written, although the warning can precede a developer's actual merge. In a retrospective study of more than 550,000 versions of nine open-source systems, the authors report textual conflicts in 16% of merges and higher-order conflicts in 33% of merges without textual conflicts. These are study-specific historical rates, not predictive performance or agent-specific rates. The paper describes Crystal's user evaluation as preliminary and qualitative. [Author-hosted paper](https://people.cs.umass.edu/~brun/pubs/pubs/Brun11fse.pdf); [DOI](https://doi.org/10.1145/2025113.2025139).

**[4] Merge-conflict classification, 2019.** The proposal's authors, title, and DOI match Owhadi-Kareshk, Nadi and Rubin. Their classifier uses nine Git feature sets, including the number of files changed on both branches and branch commit history. It consequently needs observed branch activity and cannot be used unchanged before either task starts coding. Across 267,657 merge scenarios from 744 GitHub repositories in seven languages, the authors use 10-fold cross-validation and report F1 of 0.57 to 0.68 for the conflict class and 0.95 to 0.97 for the clean class, varying by language. These class-specific scores are not PR-AUC, nor evidence of repository-held-out generalization. [Author-hosted paper](https://people.ece.ubc.ca/mjulia/publications/Predicting_Merge_Conflicts_in_Collaborative_Software_Development_2019.pdf); [authors' artifact](https://github.com/ualberta-smr/conflict-prediction); [DOI](https://doi.org/10.1109/ESEM.2019.8870173).

**[5] MergeGym and lineage, 2026.** The supplied [arXiv:2610.04779](https://arxiv.org/abs/2610.04779) exists and matches the stated title and authors. Its [full paper](https://arxiv.org/html/2610.04779) separates three questions. T1 predicts whether two PRs eventually share an authored file using PR title, body, timing and optional metadata available at PR opening. Its repository-held-out test has 5,387 pairs from 229 repositories, enriched to 39.93% positives; the training set contains 24,283 pairs from 870 repositories. The authors report pooled AUROC 0.644 for TF-IDF cosine and 0.704 for a zero-shot LLM. Their LLM plus open-time features reaches 0.740 under five-fold out-of-fold fusion. These are file-overlap results, not textual-conflict PR-AUC. PR opening need not precede coding, and the paper does not establish that both PR bodies were available before either task began.

The same paper's lineage model targets replayed textual conflicts but uses authored files and merge-base-to-head history, so it operates after changes exist. On a stratified 715-pair set, 167 pairs conflict, including 79 with disjoint authored file sets. The repository-held-out test contains 497 pairs, 117 conflicting; its 12-feature logistic model reports AUROC 0.882 and average precision 0.661, and its random forest 0.902 and 0.701. These scores concern that enriched test distribution and post-change features, not the proposed pre-start setting. The authors reconstructed 48 of the 79 disjoint-file cases and obtained clean merges for all 48; 31 were inconclusive. They do not establish that every case was uniquely caused by the other PR rather than branch staleness. Its T3 frozen-label scheduler reports median 91.7% de-overlap of labeled scope collisions at 65.0% makespan inflation over 97 repository streams. That is simulated scope overlap, not demonstrated prevention of real textual conflicts. The paper also reports median local merge replay of 0.02 seconds and does not claim prediction saves time when that exact checker is readily available. [MergeGym paper, sections 4 to 6](https://arxiv.org/html/2610.04779).

**[6] Agent PR prevalence and conflicts, 2026.** The supplied [arXiv:2607.04697](https://arxiv.org/abs/2607.04697) exists and matches the stated title and authors. The [paper](https://arxiv.org/html/2607.04697) studies 33,596 agent PRs across 2,807 AIDev-pop repositories. It samples one co-active pair per repository in each stratum: 625 same-agent and 122 cross-agent pairs. Git merge replay yields 716 evaluable pairs out of 747; 25 references were force-deleted and six lacked an accessible merge base. The authors report 119/601 same-agent pairs conflicting and 48/115 cross-agent pairs conflicting. The sample is stratified and cross-agent repositories are deliberately included, so 167/716 is not an unbiased overall conflict prevalence. The association between agent composition and conflict is descriptive, not a causal estimate. The study measures existing PR heads; it is not a pre-coding prediction experiment. Its [author replication repository](https://github.com/Quantum535/concurrent-agentic-prs-replication) describes the pair-level data and replay scripts.

## Data, benchmarks, and claim

[AIDev](https://arxiv.org/abs/2602.09185) supplies historical agent PR activity, and its [dataset card](https://huggingface.co/datasets/hao-li/AIDev-7.6M) describes the current release. Neither a linked issue nor a PR body automatically proves what was known to both agents at task start. Issue revisions, comments, repository history, assignment time, and agent identity must be checked against a defined common prediction cutoff. Retrospective co-activity selection uses later completion information: results therefore describe that selected population, not all tasks available to a scheduler. Split by repository and keep shared PRs together; check overlap with the 747-pair sample before treating it as external validation.

[CooperBench](https://arxiv.org/html/2601.13295) has 652 evaluated feature pairs drawn from 199 features in 52 task sets across 12 repositories. It evaluates agent collaboration, not a ready-made dataset of pre-start textual-conflict labels. A compatible external test requires generating and documenting the Git replay labels and preserving the pre-execution inputs. [AgenticFlict](https://arxiv.org/abs/2604.03551) is another relevant primary source: the authors report over 107,000 successfully processed agent PRs and 29,000-plus conflict cases in a PR merge-simulation dataset. Its PR-level setting is not automatically equivalent to two co-active tasks or an independent evaluation set.

The defensible claim is a proposed evaluation, not an established first: **predict pairwise Git textual merge conflict risk for two agent tasks using only task descriptions and repository information available before either task starts, and test whether predicted file footprints improve over direct text and metadata baselines on held-out repositories.** In the sources checked, TAITIr is closest on pre-implementation footprint prediction, Cassandra on scheduling, and MergeGym on agent PR scope prediction and lineage. None of those cited evaluations establishes precisely this combination of input cutoff, target and population. This is a bounded search, not proof no other paper has done it. Any performance or scheduling benefit remains a hypothesis until measured.

A useful comparison should include text similarity, a direct classifier, predicted-overlap ablation, and where feasible an acceptance-test or declared-file baseline. Report actual replay conflicts separately from shared-file proxies, calibration and the precision-recall tradeoff, and simulated wait time alongside conflict exposure. Frozen historical outcomes cannot prove what an agent would have changed after being delayed or rescheduled. Replay labels also depend on chosen heads, bases and Git configuration; record them and report unavailable pairs separately.

The [Zenodo DOI](https://doi.org/10.5281/zenodo.21186464) returned an inaccessible redirect through the search tool, and the direct record page was also inaccessible. No missing proposal reference was substituted, no dataset was downloaded, and no model or replay was run. A broader search for natural-language task descriptions predicting actual merge conflicts before both tasks start may find additional work; absence from this note is not evidence of absence.
