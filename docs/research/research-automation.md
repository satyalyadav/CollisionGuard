# Research automation for CollisionGuard

Research date: 7 November 2026. This note examines the two projects' current public documentation and selected source, not an installation or live test. CollisionGuard predicts whether two coding tasks will later have a textual merge conflict using only information available before either task starts. Its immediate priority is a defensible data pilot and reproducible baseline, as described in the [research overview](overview.md).

## Plain-language answer

Both projects may help later, but neither is needed to start the data pilot. OpenResearch is a workspace for coordinating research agents, compute, and experiment records. Karpathy's autoresearch is a small example of an agent repeatedly changing a model, measuring it against a fixed validation rule, and keeping or discarding changes. The second project's method is the more direct inspiration for trying CollisionGuard classifiers. Neither project supplies CollisionGuard's labels, leakage controls, or evidence that its predictions are valid.

ASU Sol access may eventually provide compute for experiments. Access alone does not establish that either project works there, that a particular model provider is available, or that API calls are free. First produce a small audited dataset, repository-disjoint splits, a fixed evaluator, and a CPU baseline. Then consider a bounded agent-assisted experiment. There is no need to install or integrate either project now.

## Where ASU Sol fits

The user reports that the team has access to ASU Sol. ASU lists CPU, high-memory, and GPU resources, with access and availability depending on the allocation and queue. This investigation did not authenticate to Sol or verify the team's allocation. [ASU hardware documentation](https://docs.rc.asu.edu/supercomputer-hardware/)

For CollisionGuard, possible later CPU workloads include larger merge-replay batches, preprocessing, and repeated classifier experiments. A GPU could help compute task-text embeddings at scale or run a locally hosted model. These are candidate uses, not measured speedups. The small provenance pilot and simple classifiers can start locally; a larger machine cannot recover missing historical task instructions.

ASU uses Slurm to allocate resources and run batch jobs. Its guide distinguishes the shared login node from compute nodes intended for demanding work. A possible setup is to keep the research agent on the workstation and submit bounded experiment jobs to Sol, returning metrics and logs to the project. Use the existing compute allocation rather than assuming SSH access alone grants resources. Before automation, verify connectivity, software compatibility, resource requests, time limits, and actual cancellation with one small job. OpenResearch's advertised Slurm support does not establish Sol compatibility. [ASU scheduling](https://docs.rc.asu.edu/schedulers/), [new-user guide](https://docs.rc.asu.edu/new-user-guide/)

## OpenResearch

The [OpenResearch README](https://github.com/alphaXiv/OpenResearch/blob/main/README.md) describes a local-first workspace that launches coding agents, connects literature search, and records experiments, logs, code, and artifacts. It advertises support for Codex, Claude Code, OpenCode, Cursor, and Antigravity, plus local-model options through OpenCode. In principle, a team could use its dashboard to review separate CollisionGuard experiments and their evidence. These are project claims, not features independently tested for this study.

Its support for remote compute is more than a generic suggestion to write a custom wrapper. The [CLI source](https://github.com/alphaXiv/OpenResearch/blob/main/src/main.rs) exposes an `ssh` backend for a detached process on a configured host and a `slurm` backend for a batch job submitted through a cluster login node. It also exposes Slurm CPU, memory, GPU, and time requests. The source describes the local run engine submitting jobs and recording status and logs. This establishes that these interfaces exist in the inspected source, not that they work with Sol's configuration or policies. In particular, the source says an omitted Slurm timeout falls back to settings or the cluster limit, so specify one rather than assume a short default. An [open project issue](https://github.com/alphaXiv/OpenResearch/issues/744) reports that runs on an unreachable SSH or Slurm host can remain marked running and cannot be cancelled. Check the issue and actual job state before relying on cancellation.

The [project's skill documentation](https://github.com/alphaXiv/OpenResearch/blob/main/SKILL.md) says local project and run commands do not require an OpenResearch token, while managed OpenResearch compute requires login. The [CLI source](https://github.com/alphaXiv/OpenResearch/blob/main/src/main.rs) says managed compute is billed to an organization, Hugging Face jobs to the user's account, and Modal to the user's account per second. Separately, the chosen coding agent or model provider may require its own login, subscription, API key, or usage charges. Verify the actual provider and account terms before running; a local workspace or Sol allocation does not itself pay for an external model API. The README also says official builds send opt-out usage analytics and agent feedback, so review its settings and data handling before use.

## Autoresearch

The [autoresearch README](https://github.com/karpathy/autoresearch/blob/master/README.md) describes a deliberately small single-NVIDIA-GPU nanochat language-model training setup. Its agent edits `train.py`, trains for a fixed five-minute training budget, evaluates validation bits per byte, and keeps or discards changes. `prepare.py` contains fixed data preparation and evaluation, while a human controls agent instructions in `program.md`. The [instructions](https://github.com/karpathy/autoresearch/blob/master/program.md) direct the agent to establish a baseline, record results, and repeat; they are instructions to an external coding agent, not proof that any proposed improvement is correct. The default instructions call for continuous experimentation, so CollisionGuard should replace that with explicit stopping limits.

The original data, language-model metric, GPU requirements, and training code do not directly solve task-pair classification. Borrowing the experimental method does not require copying that setup: ordinary CPU classifiers can use the same propose, evaluate, log, and keep-or-revert pattern. Whether it helps CollisionGuard is a hypothesis until tested.

## A practical later experiment

After the data pilot passes and the team has a reproducible baseline, freeze the task-pair labels, permitted pre-start inputs, repository-disjoint train and validation splits, evaluation code, primary metric, and resource budget. Keep the final test set inaccessible to the agent and use it only for the preplanned final evaluation. The agent must not change the labels, splits, evaluator, or test data. Train any learned feature transformations only on training data, and produce any training-stage predicted-file features out of fold. These are recommendations for this project, not guarantees supplied by either tool.

For example, start with a CPU TF-IDF and logistic-regression classifier using task descriptions. Ask an agent to propose one allowed change, such as adding similarity between predicted file paths available before coding. Run the baseline and candidate on the same frozen validation split and evaluator, with the same declared compute budget. Log the code revision, configuration, seed, runtime, validation average precision, and outcome. Keep the candidate only if the predeclared comparison favors it and a person checks that the feature and training procedure respect the input cutoff. Otherwise revert it. The final test remains excluded from every such choice.

A sensible first trial might allow at most five candidate changes, one job at a time, a fixed per-run time and memory limit, and a total CPU-hour and model-API spending cap set before starting. Stop on the first exhausted limit or a failed integrity check. Repeated selection can overfit even a frozen validation set, so report the number of trials and confirm the selected approach on the untouched final test. Treat a small validation gain as uncertain, not proof of improved real-world scheduling.

OpenResearch could later organize these runs if its interface saves more effort than a simple script and results table. Start with the simple local approach, then test any remote connection and provider credentials separately before relying on them. Neither repository was installed or run for this assessment; compatibility, costs for a particular account, and experiment performance remain unverified.
